# Decisions

Newest at the bottom. Each entry: what, why.

## 2026-11-18

1. **Fresh start.** The prototype (`mwf-impact-tracker`) was built on assumptions now dropped (QuickBooks input, product catalogue). OUTCOMES starts clean, module by module. Prototype code is reused only when reviewed and approved.

2. **Salesforce is the only data source.** QuickBooks is not an input. QuickBooks product tiers (main pot, sub pot, event pot, clearing pot, one product per child) were a workaround for features QuickBooks lacks. Salesforce is more structured.

3. **Transactions are instruction tokens.** We keep what is needed to deliver and report, not to account for money.

4. **No product catalogue.** Instead a small **Project Rules** table: Salesforce **Outcome Activity** to framework (e.g. "Orphan Sponsorship Where Most Needed" to Orphan Sponsorship, 12 months, quarterly report). Expected size: under 100 rows.

5. **Routing key is Outcome Activity, not Designation.** Designation is the fund (e.g. EVENTS, GENERAL AID). Orphan sponsorships taken at events sit under the EVENTS designation; only the outcome activity says "Orphan Sponsorship".

6. **Beneficiaries live in OUTCOMES.** The 2,015 QuickBooks "child products" (IDs like N-A-0365, N-H-0885) become beneficiary records here. Allocation of sponsors to children happens in OUTCOMES.

7. **No duplicate donor profiles.** Store the Salesforce donor ID and a display name. Everything else stays in Salesforce. Later: read and write back through the Salesforce API (connected app).

8. **Centres.** Centres are locations / clusters / agent regions. They send bulk batches.
   - Every gift through a centre keeps the centre as **soft credit** (`Affiliation__c`).
   - If the gift has no individual donor, it is booked to the centre (`Type__c = Community Centre`). Then **the feedback report goes to the centre**.
   - Each line stores: `creditTo` (centre) and `reportTo` (donor, else centre). Centre-only lines are flagged "no individual donor" so staff can add one later.

9. **Every field is configurable.** Per source: map column to standard field, or drop it. Add custom fields: MANUAL (staff fill) or CALCULATED (rule). Each field has type, required flag, transform, default, privacy level.

10. **Drag and drop UI** where users match or sort: field mapping, project rules, import exceptions, allocation, approvals, report templates. Auto-suggest first; users drag only the exceptions. Bulk actions and settings stay as plain forms.

11. **Structured for handover.** See coding standards in `CLAUDE.md`.

## 2026-11-18 (answers from Faisal)

12. **Hosting and Salesforce link.** Developers will build OUTCOMES in the front-end CRM. Its endpoints will feed into Salesforce. So the code needs **API nodes** (a small, separate layer that talks to Salesforce) while business rules stay pure. Salesforce data will sync with OUTCOMES later; for now we work from file uploads.

13. **OUTCOMES sends the donor feedback reports**, not Salesforce. A log can be written back to Salesforce later through the API nodes.

14. **Animal Sacrifice is a Transactional project** (with Water, Rebuild/House, Masjid, Collective marriages).

15. **The OSP Sponsorship System (earlier artifact) is discarded.** Its rules and data are not carried over. OUTCOMES starts fresh.

16. **Transaction classification fields (8).** Every transaction record has these fields, always present: **Channel, Platform, Merchant, Type, Method, Mode, Frequency, Settlement.**
   - Fill each from the source file where a column fits. If nothing fits, **leave it blank**. Never block an import because one is empty.
   - Each field points to a **master list** (configurable). Master lists share common fields: code, name, description, category, status, legal entity, country, effective dates, default, display order, parent, integration reference, audit history.
   - Raw file values are mapped to master values once (drag and drop), then reused.
   - Dependency rules (e.g. Cash cannot have Merchant Stripe) are **warnings only**. OUTCOMES does not reconcile money.
   - Principle: configuration says what is possible; the transaction records what happened.
   - Frequency matters most to OUTCOMES (drives sponsorship lifecycle).
   - Source model: "Transaction Configuration Management" note (Channel, Platform, Merchant, Type, Method, Mode, Frequency, Settlement; Platform is the hub for devices, merchants and settlement).

17. **Order reference must be unique per gift.** A repeated reference is a mistake in the source file, not a normal case, so the import flags it as `duplicate_reference` (never blocks). Found on the real UK file (18 Nov 2026): 50 references of the form EVO-999-999 used twice, rows 248 to 360, all Sadqah General Aid. The source sheet owner corrects them. Also found: 82 individual donors with no Salesforce donor ID (flagged as `missing_donor`).

18. **Instalments come from the source, not from OUTCOMES.** The number of instalments is normally set in the product configuration of the platform that took the donation, and OUTCOMES must not duplicate product configuration. So the Salesforce export needs to carry the count (to be requested). Until it does, a commitment with no count shows **Indefinitely**; one-off gifts stay blank; a real count in a source overrides it. Consequence for Module 2: Project Rules should not hold duration or instalment counts (this narrows the example in decision 4). Revisit when Module 2 starts.

19. **Only the Upload file is loaded each time. The code book is configuration.** The SF META tab changes rarely, so it is loaded once and saved with the setup (in this browser for now). The page calls the daily file the "Upload file". Auto-matching is as wide as is safe (exact Salesforce names, then names and aliases from other MWF sheets, marked "by name"), and a downloadable template shows the exact format that matches everything. Where the setup and code book are stored long term is for the developers (the setup text format stays the same).

20. **Automatic feed by batch.** Admin agents add gifts to the Google Sheet in batches. Each gift carries a batch number (`GiftBatch.Name`, for example GB-000000071). A scheduled job (cron) picks up finished batches that have not been imported yet, runs the saved setup and code book, and sends problems to an exceptions list instead of stopping. Nobody uploads files by hand. Rules: a gift with no batch number is held back; a batch is imported once; a batch edited after import is flagged "changed", not imported again silently. The scheduled job and the Google Sheets connection (read-only) are API nodes for the developers (decision 12). OUTCOMES holds the pure batch planner. Manual Upload file stays for testing and one-off files.

21. **Batch audit.** Items can be added to, changed in or removed from a batch after it is finished and imported. A quick audit compares each imported batch with the sheet as it is now, gift by gift (each gift has its own fingerprint, so one changed gift is found without re-reading the whole batch). It reports: **added** (a new reference under an imported batch number), **changed** (same reference, different content), **removed** (imported but no longer in the sheet) and **moved** (now under another batch). Nothing is lost silently. The audit is a pure function in OUTCOMES; running it on a schedule is part of the developers' job (decision 20).

22. **Google Sheets by Google sign-in, read-only.** The page reads a Google Sheet after each person signs in with their own Google account, using only the `spreadsheets.readonly` permission. Who can read a sheet is controlled by the sheet's sharing (Viewer), not by OUTCOMES. The access token is kept in memory only (never stored or logged) and expires in about an hour. The Google client ID is public and is entered once (`docs/GOOGLE-SETUP.md`). Google's script is loaded from accounts.google.com. A scheduled job cannot use an interactive sign-in, so the developers' pick-up job (decision 20) should use a read-only service account with the same `sheets-api.ts` logic. The sheet data is processed in the browser, and contact columns are still dropped before anything is saved. (Partly superseded by decision 24: people log in through the CRM, and the sheet is read by a service account. The manual Google sign-in stays only as a testing tool.)

23. **White-label and multi-organisation.** OUTCOMES is built so other organisations can use it, not only MWF. Every record, setup, code book, master list, role and setting belongs to an **organisation**, and one organisation never sees another's data (enforced on the server by the API nodes, tested). Words that differ between organisations (donor, centre, beneficiary, designation) and branding (name, logo, colours) are **configuration per organisation**, not fixed text. MWF terms stay as the MWF starter defaults. The pure logic already takes its setup as input, so it stays organisation-neutral.

24. **Login comes from the CRM.** The CRM already has a login, so OUTCOMES does not add its own. The CRM passes the signed-in person (id, organisation, roles) to OUTCOMES, and the server checks it on every request. OUTCOMES decides what each role may do. The sheet is read by a read-only service account per organisation (decisions 20 and 22), not with each person's Google credentials, so people only see what their role allows.

25. **Roles are configuration, not code.** An organisation admin creates and edits roles in Settings. A role has a code, name, description, status and a list of **permissions**. Permissions come from a fixed catalogue that each module registers (for example import.run, mapping.edit, beneficiary.view, donor.contact.view, report.send, settings.manage). A role also has a **data scope**: all, own group (centre, institute, house or cohort), assigned records only, or own record only. A new organisation starts from a starter pack of roles it can change. Roles that are about people in the data (beneficiary, student, carer, warden) are kept separate from login roles, see the open question.

26. **Generic model, with sources as adapters.** OUTCOMES also works standalone, for organisations with no CRM that upload files by hand or connect another way, and whose columns differ. So the solution is built in three layers: (1) a **generic model** whose field names say what a thing means, not what a source calls it; (2) **source adapters** (file upload, Google Sheet, API or webhook, and CRM connectors such as Salesforce) that bring rows in; (3) **organisation configuration** (labels, column mapping, value mapping, lookup lists, roles). Everything specific to Salesforce or MWF (column names like `Legacy_Reference_No__c`, the designation JSON, the SF META layout) moves into a **Salesforce preset** that pre-fills the mapping. It is one preset among others, and an organisation with no preset maps its own columns. Consequences: (a) a transaction can arrive as one row per transaction with a lines column, or as one row per line, grouped by reference; (b) lookup lists (IDs to names) are optional, because a source may carry names directly; (c) which fields are required is set per organisation, so a supporter ID is required only where a CRM provides one; (d) the login is pluggable: the CRM's login where there is a CRM (decision 24), otherwise a built-in or Google or Microsoft login. The coding standard "use Salesforce terms" now applies to the Salesforce preset only.

27. **Module 1 rebuilt on the generic model (18 Nov 2026).** Generic vocabulary confirmed: Transaction, Line, Supporter, Fund, Outcome, Group, Commitment. The Salesforce specifics (column names, the designation JSON, the SF META layout, MWF wording) are one preset. Lookup lists are optional configuration inside the setup. Three lines layouts. Required fields per organisation. A "feedback items only" switch skips total checks for partial uploads. New checks: future date, rows of one transaction disagree. Setup format is now version 2 (older saved setups are ignored).

28. **For MWF, configuration lives in the CRM and OUTCOMES reads it (accepted 19 Nov 2026, from reading mwf_crm).** The CRM (PHP and MySQL) already holds the catalogue (items, variants, bundles, projects, causes, campaigns, intentions), transactions (`crm_transaction`) with line items (`crm_transaction_detail`, each with item, project, cause, post and intention), payment mode, merchant, channel, agent, subscriptions, roles with data scope, and a Salesforce push. So OUTCOMES does not keep its own product or project configuration. A **CRM feed** supplies paid transactions and lines plus the reference lists (items, projects, causes), and OUTCOMES creates **work orders** from lines that need feedback. In OUTCOMES this is a preset ("MWF CRM") next to the Salesforce preset, so other organisations are unaffected (decision 26). The CRM item already has `item_recurring` and `frequency` (for example 12), so the instalment count of decision 18 can come from the catalogue. The CRM has no "needs feedback" or framework flag yet, so one must be added in the CRM, in one place. Answers from Faisal: the feedback trigger is at **item level**, and the feed is a **database view**. Nothing in the CRM repo has been changed.

29. **OUTCOMES is standalone and takes its configuration from the organisation's CRM (19 Nov 2026).** The things needed to manage work orders (instruction tokens) are universal: any charity that sends feedback reports has them configured in its CRM one way or another (items, which need feedback, instalments, payment details, supporters). OUTCOMES does not duplicate them. A CRM connector (a preset plus a read-only database view or equivalent) maps the CRM's fields and extracts its configuration, so the configuration stays in sync with the CRM and has one source. OUTCOMES then focuses on the **work order, the token and the project journey** (routing to a framework, delivery, tracking, feedback reports). Where the CRM already does something, OUTCOMES uses it rather than rebuilding it: **email and communication** go through the CRM, and the **supporter profile** is viewed in the CRM interface. OUTCOMES keeps only the supporter ID and display name (privacy rule). An organisation with no CRM still uses upload or Google Sheet sources and its own setup (decision 26).

30. **Independent build, two ways in, and reporting back (19 Nov 2026).** OUTCOMES is built independently of the CRM repo and branches (nothing is built on the CRM branch). MWF adds the item-level "needs feedback" trigger in the CRM itself, in its next push. The connector can read the CRM **through a database view or through an API**, so it is a pluggable reader behind one interface, and the choice is per organisation. The link is two-way: the CRM is the **data input** (transactions, lines, items, instalments), and OUTCOMES **reports back to the CRM** (delivery status and feedback reports) so the CRM's donor portal and communications can show and send them. The return path is a write interface in the connector, kept separate from the read side, and it writes only status and report links, never money or contact details.

31. **Frameworks live in OUTCOMES, not in the CRM (19 Nov 2026).** Project management (frameworks such as Orphan, Hifz, Water, with their stages, rules and reports) is a gap in charity CRMs, so it is the part OUTCOMES owns. The CRM supplies only the item and the yes/no trigger "this item needs feedback" (decision 30). **Which framework an item belongs to is set in OUTCOMES**, by mapping CRM items to frameworks (auto-suggest first, then drag and drop to correct, as in Module 1). An item flagged in the CRM but not yet mapped to a framework shows as **unrouted** for staff to resolve, and never blocks. A framework is optional per organisation: an organisation with none can still receive tokens and track them with a default simple journey. Later, once matured, OUTCOMES may be embedded in the MWF CRM as a connected module, but the product stays a white-label that talks to many CRMs through connectors (decisions 26, 29, 30). So the MWF CRM item carries only the trigger, not the framework, and Module 2 (Project Rules) owns frameworks.

32. **Access comes from the CRM by a one-click launch, with no user management in OUTCOMES (19 Nov 2026).** Where there is a CRM, people sign in to the CRM and click an "OUTCOMES" button that opens OUTCOMES in a new window, already signed in. How it works: (1) the CRM shows the button only to people whose CRM role has an OUTCOMES permission (the CRM already has a Roles and Permissions matrix, so no new user panel is built); (2) clicking makes the CRM create a **short-lived, single-use, signed launch token** (lives about a minute) holding the person's id, display name, organisation, and the OUTCOMES permissions their CRM role gives them; (3) OUTCOMES checks the signature on its **server**, starts its own session and removes the token from the address; (4) the session is short and is refreshed by asking the CRM again, so removing someone in the CRM removes their access at the next refresh. OUTCOMES stores no passwords. The permission names OUTCOMES needs (for example `outcomes.access`, `outcomes.view_work_orders`, `outcomes.map_frameworks`, `outcomes.settings`) are registered in the CRM's permission matrix, and OUTCOMES' own roles and data scope (decision 25) become a mapping from CRM roles, not a second list to maintain. An organisation with no CRM still needs a login, a small pluggable one (decision 26), but that is outside the CRM-connected product. This needs a small **server part** in OUTCOMES (token check, session), which the browser-only page cannot do, so it is developer work and an open build decision (decisions 24 and 25 are refined by this).

33. **Connected mode is the main screen, import is for other sources (19 Nov 2026).** With a CRM connected, OUTCOMES shows **work orders** that arrive from the CRM feed, already limited to items flagged as needing feedback (decision 30), so there is nothing to import. The Module 1 import and mapping page stays as the way in for organisations with no CRM, and as a testing tool. The home screen should show work orders (ready, unrouted, needs review), not the import page.

34. **OUTCOMES has an application shell that matches the CRM, grown as the product grows (19 Nov 2026).** Because OUTCOMES will have many pages, menu items, frameworks and dashboards, it starts from a proper ERP or CRM style shell (side menu, top bar, page area, cards and tables) that follows the MWF CRM's look (blue gradient menu and header, Inter font, tinted page, white cards), instead of one tool page. The menu is driven by the CRM role's permissions (decision 32), so a person only sees what their role allows. The shell is in `app/` (open `/app/` with `npm run dev`). Colours are variables, so another organisation can re-brand it (decision 23). Module 1's mapping page stays reachable under "Other sources" until it is moved inside the shell. The look is plain CSS for now. Whether the developers move to a component library or the CRM's own theme is for them to decide when the stack is confirmed (open question on the stack).

35. **Item to framework mapping works by suggest, drag and drop, and never moves work in progress (19 Nov 2026).** Staff sort the CRM items that need feedback into frameworks by dragging them (or tapping an item and then a framework). Suggestions come from whole-word matches of a framework's keywords in the item name, are shown as hints and applied only when accepted, and a tie suggests nothing. Sorting an item routes its unrouted work orders, but work orders that already have a framework keep it, so delivery in progress never changes silently. Each framework holds a unit, a feedback cycle, a report type and its keywords, and no duration or instalments (decision 18). Removing a framework returns its items to Unsorted. Built as Module 2 (`modules/02-project-rules/`).

36. **Three levels: items, frameworks, categories (replaced by decision 40) (19 Nov 2026).** Many CRM items cluster into one framework (for example several orphan sponsorship items into Orphan Sponsorship), and frameworks are grouped into **categories** of framework. MWF's starting list, from the earlier discussion (confirmed by Faisal, 19 Nov 2026): **Sponsorship** (Orphan Sponsorship, Hifz, School, College/Uni, Aalim, Homestay), **Transactional** (Water, Rebuild/House, Masjid, Collective marriages, Animal Sacrifice, decision 14), **Livelihood** (Rozgar, Rickshaw), **Microfinance** (Loans), **B2B** (no frameworks listed yet). Categories are configuration per organisation (decision 23), so another organisation has its own. A category sets the feedback cycle a new framework starts with (for example Sponsorship quarterly, Transactional once when delivered), and staff can change it per framework. What else a category changes (for example sponsorship frameworks hold beneficiaries and renewals, transactional ones deliver once and report) is built with Module 5 (Frameworks) and is not decided yet. Removing a category keeps its frameworks.

37. **Hosting the demo on Vercel (19 Nov 2026).** The demo (the shell and the Module 1 page, with invented data only) is published to Vercel from this repo with `vercel deploy --prod` (project `outcomes`, settings in `vercel.json`). It is a static site, so there is no server yet and nothing is stored. The deployment is behind Vercel's sign-in (Deployment Protection), so only people with access to the owner's Vercel account can open it. No real donor, child or CRM data may be put on it. Automatic deploys on every push need the Vercel GitHub app installed on the repository, which is not done yet. The server parts (decision 32 launch token, storage, pick-up job) still need a host and stack decided with the MWF developers, and Vercel is one option (serverless functions). **Amended by decision 43:** real donor IDs and display names may now be stored, under the conditions there.

38. **Server built as Vercel functions with a swappable store (19 Nov 2026).** The server parts are Node and TypeScript in `api/` (thin) and `modules/00-platform/` (logic as plain functions, tested without a network): sign-in from the CRM launch token (decision 32), per-organisation storage, and the pick-up (decisions 20, 28 to 31). Storage is an interface with a memory version (tests, demo) and a Postgres version (Neon through Vercel), so the MWF developers can swap the database or host the same code elsewhere. Sessions last one hour and the person reopens OUTCOMES from the CRM, because refreshing by asking the CRM needs a CRM endpoint that does not exist yet. The scheduled pick-up runs daily (free Vercel plan limit), plus "Run pickup now". When someone sorts an item into a framework, its unrouted work orders are routed immediately, and routed ones are never moved. The CRM read token is never stored in the database, only the name of the setting that holds it. Until a database is connected, a temporary memory store is used and the page says nothing is kept.

39. **A pretend CRM for testing with live input (19 Nov 2026).** Until MWF's CRM has the item-level trigger and a feed, OUTCOMES can be tested against Module 1d, which behaves like a CRM: it produces a feed in exactly the CRM-FEED-SPEC format and new gifts arrive every 5 minutes, worked out from the clock so nothing is stored. Some gifts start pending and turn paid, some fail, and some are later deleted, edited or replaced, so the review list is exercised. An organisation whose CRM setting is `demo` uses it, through the same reader interface as a real CRM, so nothing in the pick-up changes. A test sign-in (`/api/demo-login`) opens the organisation `demo` as an administrator. Reason: Faisal needs to test with realtime input before the CRM work is done. Rules: the test sign-in answers 404 unless the server has `DEMO_LOGIN=1`, it can only open the `demo` organisation, and it is meant for a protected test server only. Remove `DEMO_LOGIN` to switch it off.

40. **Two levels: items and categories. The framework is a property of the category (19 Nov 2026).** Decision 36's three levels (items, frameworks, categories) meant sorting twice for one journey, because the items in a category need a similar journey anyway. Now an item belongs to a **category**, and the category has properties: its name, the words that suggest it, and its **framework**, the settings that decide the flow of every order in the category (unit, feedback cycle, report type, and later the stages). Work orders are routed to a category (`categoryId`). Sorting is one drag. The Frameworks page became the **Categories** page. The permission `outcomes.map_frameworks` keeps its name so the CRM specification does not change. Setup saved in the old shape is shown as empty and starts again from the MWF starter categories. Replaces decision 36.

41. **The CRM's feedback trigger and where instalments come from (19 Nov 2026, from reading mwf_crm again).** The CRM now has the item-level trigger: `crm_items.item_feedback` (migration 074), 1 = Acknowledgement only (the default for every item), 2 = Feedback report. OUTCOMES' MWF settings are trigger column `item_feedback`, yes-value `2`. An older saved setup with the first guess (`needs_feedback`) is moved to these automatically. **Price, frequency and instalments are not set on the item.** They are configured on the catalogue price list line, and copied onto the donation line (`crm_transaction_detail`: `id_vdetail`, `frequency`, `is_continuously`, with the plan's `installment_limit` on `crm_subscriptions`). So the feed carries `is_recurring` and `instalment_count` **per line**, and decision 18's rule stands: no count or a plan until cancelled shows Indefinitely, a one-off stays blank. This replaces the item-level `item_recurring` and `item_frequency` of decision 28. Nothing in the CRM repo was changed. The CRM has no feed view or API for OUTCOMES yet: the column sources are in `docs/CRM-FEED-SPEC.md`, for the CRM developers to confirm.

42. **Stopgap: run OUTCOMES on the CRM's Export Centre files (19 Nov 2026).** The CRM has no feed view or API yet, but it has an Export Centre. Three CSV exports stand in for the feed: Donation lines (paid, one row per line), Catalogue items (the `Feedback type` trigger per item, joined on item code = Item SKU) and Recurring plans (instalment count, joined on the line's Subscription ID = Plan ID). A pure adapter (`modules/01e-crm-export-adapter/`) turns them into feed rows in the shape of `docs/CRM-FEED-SPEC.md`, so everything after it is unchanged. Real files live in `real-data/`, which git ignores, and are never committed or printed (CLAUDE.md privacy). Known limits: the export has no centre, no deleted or replaced markers (replaced orders cannot be detected) and no line total, and a recurring line whose plan is missing from the plans file shows Indefinitely. The proper feed view or API (decision 28 to 31, 41) still replaces this later.

43. **Real data saved on the server, and the batch audit (19 Nov 2026, Faisal's choice).** Faisal wants to come back to the real data again and again, so the work orders made from uploaded CRM export files are saved in the Neon database on Vercel, not only in the browser. This amends decision 37 (no real data on Vercel). Conditions: (1) only what OUTCOMES already stores by design is saved: work orders with the CRM donor ID and a display name, no contact details, no child data (CLAUDE.md); a supporter's name is not even sent for lines that need no feedback, and channel, merchant and payment mode stay in the browser. (2) The site stays behind Vercel's sign-in, and the app needs an **owner passphrase** (`OWNER_PASSPHRASE`, 16 or more characters, held in Vercel settings, never committed) until the CRM sign-in exists. The owner sign-in opens only the organisation `mwf`, answers 404 when no passphrase is set, and the organisation always comes from the signed session. (3) Raw export files and the converted feed are never saved on the server or in git, only work orders, the setup and the audit records. (4) Decision 12 and the open hosting question stand: the MWF developers may move this to their own servers, and the Store interface keeps that possible. **Batch audit (decision 21) in the CRM world:** a "batch" is one import (an upload of export files, or a scheduled pick-up). Each import is compared with the saved work orders, line by line, and reports **added, changed** (amount or supporter), **moved** (now on another item), **no longer needs feedback** and **removed** (no longer in the CRM). Removed is judged only for work orders paid inside the dates the import covers, so a Feb to Oct export says nothing about November. The audit only reports: nothing is changed or deleted automatically, and the last 100 audit records are kept. Seen on the new Audit page.

44. **Capacity for agents, groups and organisations, built now and optional (19 Nov 2026).** In MWF's setup a rep (agent) belongs to a community group, and a group may belong to an organisation (for example a rep at a company's Manchester branch). Sometimes the agent soft-credits by name, sometimes the group gives on its own name with no agent. The CRM will hold these links but does not yet, so OUTCOMES gets the capacity now to avoid restructuring later, kept small and generic: (1) the feed may carry a **credit chain**, up to four levels of `credit_N_role`, `credit_N_id`, `credit_N_name`, nearest first, and a `supporter_kind` (individual, organisation, group); (2) a work order keeps the chain and kind when present, and nothing is stored when absent, so today's data is unchanged; (3) pure rules in `credits.ts`: an individual donor or an organisation giving in its own right gets the report, a group's own gift or a line with no donor goes to the nearest credit (agent, then group, then organisation), with no credit it stays with the donor, and "no individual donor" is flagged (decision 8); (4) the chain is for roll-ups too, so a group or organisation can later see everything credited to it. Roles are the CRM's own words and are not interpreted. OUTCOMES keeps **no separate list** of agents and groups: the CRM's links are the source. The Module 3 screens (roll-ups, adding an individual donor later) are built when the CRM provides the data. Names in the chain are sent to the server only for lines that need feedback, as for donors (decision 43).

45. **Module 4 is the Needs attention list (19 Nov 2026).** Most of what the roadmap called "import and triage" already exists: files go through the adapter, lines become work orders, items are sorted into categories, and a re-import never duplicates a work order (decision 43). What was missing is one place for everything that needs a person. The **Needs attention** page gathers: items not yet in a category (one entry per item, cleared by choosing a category, never by marking reviewed), problems found while converting or reading an import, and changes the audit held for review (changed, no longer needs feedback, no longer in the CRM). A person can mark an entry reviewed, with a short note, and reopen it. The list is rebuilt from the saved data each time, so an entry clears by itself when its cause is fixed. Rules: nothing here changes a work order; reviewed marks are saved per organisation and keyed by a stable id, so they stick across imports; marking reviewed needs the permission to map items, viewing needs the permission to view work orders; import problems describe the latest import only. The earlier idea of dragging to fix an exception is covered by choosing a category on the entry, and wider fixes come with later modules.

46. **A work order is keyed by the CRM line id alone (19 Nov 2026).** The key used to be "order reference : line id". In the real export 5,787 of 7,736 lines have no order reference, so a reference added later would change those keys and make duplicates. The line id is unique and never reused (CRM-FEED-SPEC), so it is the key. The order reference stays on the work order as a displayed field. Work orders saved under the old key are moved automatically at the next pick-up or import, keeping their category, status and review entries, with no duplicates. The batch audit, the review list and Needs attention use the new key, and report-back statuses are sent once more. Repeated import notices are now grouped with a count, and the page shows at most three.

47. **Exclude a work order, and mark guessed instalment counts (19 Nov 2026).** A person can exclude a work order that has not started (unrouted or ready) with a required reason, for example a payment made during development and bug fixing. It is not deleted: it stays on file with the reason, who and when, so a re-import never recreates it (its line id is already known). Excluded work orders leave the active list, the counts and the dashboard, are not audited, never raise review entries, and show under an Excluded tab with a Restore button, which puts them back where they were. Started work (in progress, delivered, reported) cannot be excluded. Needs the permission to map items. 50. **Units: one catalogue item is one unit, and the bundle configuration sets the multiplier (19 Nov 2026, rule from MWF, not built yet).** A recurring item is a single item in the catalogue, and one unit is one period of it (for example one month of an orphan sponsorship at 40 pounds). A monthly sponsor gives one unit per instalment, so a 12 month plan is 12 units across 12 work orders. Someone who pays for the whole year at once gives one line, and the **bundle quantity** in the CRM's bundle configuration says how many units it is (12), so it covers 12 months of the same outcome. Allocation will therefore count **units**, not lines or money: a work order carries a number of units, and the units are what is allocated to an outcome. Not built: the real export shows one-off lines with Order Quantity 1 and an amount of 10 times the monthly price (for example 420 against 42), so the bundle quantity is not in the Donation lines file and must come from the bundle configuration. Worked example from the donation page (orphan care): the base unit is one **part** of an orphan sponsorship for one **month**. A part is 40 pounds a month, or 480 pounds for a year paid at once (12 units). One orphan takes three parts, so "Sponsor an Orphan" is 1,440 pounds a year (3 parts x 12 months = 36 units), two orphans 2,880 and three orphans 4,320. So units come from two things set on the item: the parts in the bundle, and the months the period covers. The real data shows the price per unit has changed over time (35 pounds a month, 420 a year, 70 for two parts), so units cannot be worked out from the amount. Open: which Export Centre file or field holds the bundle quantity, and whether the unit count should be read from it or worked out as amount divided by the unit price. Decide this when the allocation module is started.

51. **Parts are read from the bundle, never from the price (19 Nov 2026).** Bundles are set on the item in the CRM (name and quantity, for example Sponsor an Orphan = 3 parts of the Part Sponsorship item). The Donation lines export has an optional **Item Bundle** column and the **Catalogue prices** export lists each bundle with its quantity. The adapter joins them by item code and bundle name: a line's `bundle_qty` is that quantity, blank when it has no bundle, and a work order's parts are `bundle_qty` x order quantity. Prices are ignored on purpose (an old price does not matter, and custom amounts are not triggered for feedback). A bundle name the prices file does not know counts as 1 part and is reported once. With no prices file, bundles count as 1 and a note asks for it. A work order made before this keeps working: it is quietly given its bundle quantity at the next import, with no review entry, because it is catalogue data and not a donor change. 52. **Two ways an instalment relates to a unit, chosen by the category (19 Nov 2026, rule from MWF, not built yet).** The catalogue splits an item's price into instalments for almost every item (for example a Small Pump is 180 pounds, or 18 pounds times 10), so the price structure cannot say what a unit is. It depends on the kind of item, which is what the category stands for. (1) **Time based** (sponsorships, scholarships): a unit is one part for one month, each instalment is 1 unit, and a payment made at once is as many units as the plan has payments (decision 50). (2) **Price split** (water pumps, wells, buildings, and other things delivered once): a unit is the whole item, each instalment is a share of one unit (1/10 of a pump), a payment made at once is 1 unit, and the unit is complete, and can be delivered and reported, only when all its instalments are paid. Parts from the bundle (decision 51) multiply units in both. The number of instalments comes from the catalogue plan or the subscription. This switch becomes a setting on the category when allocation is built, and the Commitments view should show "4 of 10 paid" for a price split item.

59. **Frameworks are reusable templates, chosen by category and by item (20 Nov 2026, replaces decision 40's embedded framework).** A framework is defined once and used by any number of categories and items, so a framework needed by two categories is not defined twice, and a small difference between items does not need a new category. A **template** holds: name, unit, feedback cycle, report type, how an instalment counts (decision 58) and **units per beneficiary** (a whole number: 3 parts make one orphan, 1 for a whole scholarship). A **category** has a default framework. An **item** can pick its own. The framework that applies is the item's own, otherwise its category's, otherwise none. For a small difference, duplicate a template and change that setting. Field by field overrides on an item were considered and left out, because what applies to an item would then be hidden. A work order keeps the framework it was routed under (`frameworkId`): changing an item's framework later moves no existing work, while editing the template itself applies to all work that uses it. A template that a category or an item uses cannot be removed. Bundles never create a different framework: they multiply the units of the same one, and the units of allocation are the base item for one period (decision 50). Units per beneficiary tells allocation how units pack into beneficiaries: parts equal to or above it are dedicated to the donor (3 parts a month is one orphan), the remainder is a share pooled with other donors, and 1 per beneficiary means every unit is a whole beneficiary. The Commitments page shows this. The pooling rules themselves belong to the allocation module. A setup saved with a framework inside each category is moved to templates automatically (identical ones are shared) and nothing sorted moves. MWF's starting templates (to be confirmed): Sponsorship: shared parts (3 per child, per period), Sponsorship: whole (1 per student, per period), Delivered once (a share of a whole), and Livelihood and loans. Starting use: Sponsorship defaults to shared parts, and items named Hifz, Quran, school, college, university, Aalim or Homestay are suggested the whole framework, for a person to accept. Orphan Care Home is a construction project and belongs under Transactional with its own stages, which come with that framework type.

60. **The journey from gift to outcome (20 Nov 2026, vision agreed with Faisal, not built yet).** A framework is the link between an **outcome** and its **unit of allocation**. An outcome is any of: a child, a student, a widow, a tutor, a bride, a building, a location, an activity. The journey is five steps: (1) donation, the paid lines from the CRM; (2) commitment, the lines that belong together (a subscription's instalments, or a one-off for a whole period); (3) units, worked out from CRM data (bundle parts, instalments, the plan's length, decisions 50 to 52, 58); (4) allocation, the units fill an outcome in the order the donations were given: a one-off fills its whole period at once, monthly instalments fill one month at a time; (5) availability, each outcome shows how full it is (open, part funded or full), and a full one is no longer offered while a part funded one still takes new commitments. A framework says what the unit is, how much capacity one outcome has (for example an orphan has 3 parts a month, a student 1, a pump 1 whole filled by shares) and how a payment becomes units. Rules agreed: (a) **capacity lasts as long as the cohort is active**, with no fixed window. A donor whose subscription nears its end is reminded to continue, and if they do not, that capacity is allocated to someone else. (b) A subscription with a defined limit is **forecast**: its upcoming payments show **orange**, and **red** when an expected payment did not arrive, so an outcome counts as forecast sponsored because a subscription is allocated to it. (c) A subscription with no limit stays allocated for as long as payments keep coming in, and if the cohort is made inactive it is **reallocated** to another available one. (d) **Allocation is automatic** to whatever has capacity, and there must be a way to **reallocate at a donor's request**. (e) **Cohort management comes later**, but a commitment must connect to an allocation whatever the outcome type. Needs from the CRM, already exported: a plan's status, Next due, Last paid and Instalments paid, which give the expected and the missed payments. To build, in order: the Outcome and capacity model with availability, then the allocation rules and the forecast colours, then reminders (sent from the CRM, OUTCOMES only says who is due), then cohort management. The Frameworks screen built under decision 59 is to be reworded to match this vocabulary: commitment, unit, outcome, capacity, allocation, availability.

62. **Outcomes are drawn as a row of months, each month a small pie with a slice per unit (20 Nov 2026, corrects decision 61's single pie).** Faisal's picture: one line per outcome, months across, and for each month a small pie whose slices are the outcome's units (an orphan has 3 parts, so 3 slices), each slice coloured by status, with the outcome's availability (open, part funded, full) at the end of the row ("Now"). Colours are status, never donors: paid green, expected orange, missed red, nothing expected grey. A slice that holds a commitment opens it, and the commitment holds the donor. The window is five months back, the current month and six ahead. For this the plan's own facts now travel with each line from the Recurring plans export: **plan status, next due date and instalments paid** (new feed columns `plan_status`, `plan_next_due`, `plan_paid`, kept quietly up to date on the work order at each import because they change as a plan goes on). Rules: a month with a real payment is paid. A plan that is going has a run of expected months starting at its next due date and lasting for the instalments it has left (for ever with no limit). In that run, a past month, or this month once the due date has come, is **missed**, and a later month is **expected**. A paused plan expects nothing ahead. A cancelled or completed plan expects nothing, and a plan the CRM has cancelled **stops holding capacity**, so it reopens for someone else (decision 60a). Legacy openings are not payments and do not colour a month. On the real data: 66 commitments are 53 active, 7 paused, 5 cancelled and 1 completed, 61 of them hold capacity. Over the twelve months that gives 164 paid, 319 expected, 35 missed and 214 nothing expected. Not built: one-off payments, reminders, cohort management.

64. **One-off payments are allocated too (20 Nov 2026).** A single payment for a per-period item (an orphan paid for a year at once, a scholarship paid for ten months) fills an outcome for the months the item's plan covers, instead of being left out. Rules: (a) the months a single payment covers are the **length of the item's instalment plan** in the CRM's catalogue (480 once, or 40 for 12 months, is 12 months). It comes from the Catalogue prices export (`Way of giving` Instalments, `Payments`, for the item and bundle) and travels as a new feed column `period_count` on one-off lines. An item that continues until cancelled has no length, so a single payment of it covers one month. (b) The covered months run from the month it was paid, all **paid** (green), since the money is already in. (c) It takes its parts (bundle times quantity) for those months only. After the last covered month it is complete and the parts are free again, so the outcome can be offered to someone else. (d) Only items whose framework counts each instalment as a period (per period) are included. A water pump or other whole item paid once is not, because it holds its whole for good and shows no months. Legacy uploads, excluded work orders and recurring lines are left out. (e) One-offs are **not** listed on the Commitments page, which is about subscriptions. They appear in Outcomes, where a slice opens them as "One payment <line id>" with the donor. (f) A one-off whose length is not in the prices file counts as one month. Real data: of 198 one-off feedback lines, 187 get a length (146 of 10 months, 41 of 12).

A note on 64 (20 Nov 2026): a work order keeps the framework it was routed under (decision 59), so changing a category's or item's framework did not reach work orders already made, and Outcomes found no commitment asking for capacity. The Categories tab now has **Apply frameworks to existing work orders**, which a person presses to move every work order to the framework that now applies to its item. It is never done by itself. The Outcomes tab also says why commitments are not asking for capacity.

65. **Projects: each defines its own structure (20 Nov 2026, agreed with Faisal; step 1 built).** A project is somewhere that sponsors people or things (Aghosh Orphan Homes). (a) Each project defines its **own levels** as a chain (for example Branch, Block, Class), with names and depth of its own. **Location is a field on the Branch profile**, not a level. (b) **Cohort is not a separate thing**: a class is simply a level if a project wants one, and admission date and progress will live on the beneficiary's profile (profile fields come later, with private ones for child data). (c) A project defines **types of beneficiary** (child, teacher, carer, warden), each living at a chosen level and sponsored by its own framework, so a gift for one cannot land on another. A student and a teacher are told apart by the item, through its framework. The category model stays: items go in categories, a category has a default framework, an item can override it. (d) Beneficiaries are the existing outcomes, now tied to a project, a place and a type. Those made before projects existed stay as they are. (e) A gift's project is the CRM's **Project** on the donation line. It is matched to a project by name or alias. A match is a **directed** gift and fills that project only. "Where Needed Most" or blank is a **general** gift and can fill any project. On the real data about 91 percent of feedback lines are general and 9 percent directed. General gifts are **spread** across places, and a directed gift whose project is full **waits** for a person (not built yet). (f) Items that match no project or category can be matched by hand. (g) One-off **activities** (solar panels, a classroom renovation, furniture, a party) are not sponsorships. They have a target in units (one whole unless an item says otherwise), are matched by item, and move through stages with reports, which belong to the framework. Vendors will post verified updates with photos, video and locations, and a vendor portal comes later. Not built: allocation across projects (next), activities, profile fields, vendor updates. 68. **Partners, and the whole flow from donor to donor report (20 Nov 2026, from Faisal).** **The flow:** (1) a donor picks an item from different pages of the website or the point of sale. (2) Different partners deliver different projects. (3) A partner (vendor) is whoever implements the job of a gift, and may be an institute, a contractor or another charity. (4) An institute has a cohort managed in layers, and (5) may have several branches, each with its own cohorts. (6) A partner is given a **batch** of orders, and the batch's progress is tracked to manage implementation deadlines. (7) A batch holds orders (commitments), and (8) each commitment is given an **outcome**. (9) A commitment carries information the vendor needs to implement it, such as the **tribute name**, which is in the CRM. (10) The vendor updates each order with the prerequisites we define (fields, photos, video, locations). (11) Our office verifies the vendor's input and approves, and then the donor is sent their outcome. **Decisions:** (a) What was built as "Projects" is renamed **Partners** on screen and in the menu: it is an institute's structure and a partner's profile. The code still calls a partner a `Project` and will be renamed later. (b) The CRM's **Project** is the page of the website the donor posted from. Items are general, so a general item such as Orphan Sponsorship bought from the AGHOSH page carries the project name Aghosh, which makes it a specific gift. (c) Sponsorships are not matched by a person. They are either **auto assigned** (general) or **specifically assigned** to a partner (directed), as built in decision 66. (d) A CRM project name may go to **more than one partner**, and a partner may answer to several names. A gift for that name can go to any of its partners and is spread across them. In the list of CRM names each name has a tick box for every partner. (e) Partners are set up in OUTCOMES, because the CRM does not manage outcomes. A partner has a type (institute, contractor, another charity), the CRM names it answers to, and for an institute its structure. (f) Orphan sponsorship is fulfilled by several institutes, and water pumps by several vendors. (g) **Pump jobs are given to vendors by a person**, by capacity, which is a judgement. 71. **Places and groupings, not a chain of levels (20 Nov 2026, corrects decisions 65 and 70).** Faisal's point: Class, House and School are not nested inside each other. A partner has many of them, each with its own profile fields such as a location. (b) Every other level sits under a level as a **grouping inside a place** (Class, House, School). (d) A **beneficiary** belongs to one place and to at most one group of each grouping that applies, and the group must be inside that place. (e) A place or group adds up its own beneficiaries once (a child in a class and a house counts once at the branch), and a gift dropped on a group goes to someone in that group. (f) Automatic allocation spreads gifts across the **places** (branches) first, then fills a partly sponsored beneficiary first inside a place. (g) On screen, the form for adding beneficiaries asks for the type first, then offers only the places of the right level, then asks for the groups that apply in that place. A level cannot be removed while it has levels under it, places, or a type that uses it. 84. **A payment can cover more than one instalment, and OUTCOMES suggests which (22 Nov 2026, from Faisal: a failed payment is sometimes taken together with the next month, hence a double payment).** A work order gets an OUTCOMES-owned field `covers` (absent = not checked, 1 = checked and normal, 2 to 6 = a catch-up). It is never sent back to the CRM and survives CRM refreshes. **Suggestion method (no AI, so it is explainable and portable to Apex):** the usual value is the value that most of a gift's payments share (at least two must). A payment worth 2 to 6 times that, within 2 percent, and not yet checked, is suggested as a catch-up, and the gift gets the note "Possible catch-up payment" and goes to Needs a look. **Which months it fills:** a gap before the payment comes first, nearest first. With no gap it covers the month before, and the one before that. It never fills a month another payment covers. The same date on two payments is no problem, since months are what count. **Effects once a person agrees:** paid counts the instalments covered, the paid months include the filled months, and parts per instalment are the payment's parts divided by what it covers (so 2 parts on a 70 payment covering 2 are 1 part each and the "parts differ" flag clears). A person decides each time with "Yes, it covers 2" or "No, it is a normal payment", or the Covers drop-down on a payment in the gift window. A later option is to let a language model read odd cases, but the rule based suggestion comes first because it can be explained to the donor team and ported to the CRM.

## 148. The bare minimum to configure a type (23/11/2026)

## 152. Project, cluster and beneficiary, with roles (23/11/2026)

Design agreed with Faisal, not built yet. Supersedes the cluster definition in 143, and replaces the earlier idea of retiring the Projects page.

- **Structure:** Project, then Cluster, then Beneficiary. A **project** is what the donor chooses (matched to the CRM project name on the gift). It houses **many benefits** (gift items) and is not tied to a workflow, since each benefit brings its own workflow. It names its **implementing partner or partners** (one or several). If it names none, the partner assigned at Assignment implements it. A **cluster** groups beneficiaries inside a project: regions, classrooms of a care home, tent villages in a flood relief project, medical camps in an eye clinic project. Clusters can sit under each other (Region, then Classroom), a project may have none, and a beneficiary belongs to one cluster and one project. Cluster and project are no longer the same thing, and "project" belongs only to the donor's choice.
- **Reuse:** the levels and places engine of the partner structure (decisions 65 and 71) is the cluster engine. It is moved from the partner to the project, and the structure already built on partners converts into project clusters. Cluster capacity or target uses the existing fill counts.
- **Cluster properties:** a name, a level label defined per project, a place, a capacity or target, a status, a roll-up report (for example 14 of 20 tents delivered), and **roles**.
- **Roles on a cluster** (Faisal's examples: case worker, warden, mother, team leader, supervisor, evaluator, sign-off supervisor, caretaker, site engineer): the roles are **configurable labels**, not fixed, set per level so a classroom, a tent village, a camp and a build site each have their own list, and each cluster names the person in each role. The role holders are chosen from the partner's contacts, or added. They are partner staff: their contact details are for MWF and the partner, never shown to donors.
- **Roles in the flow:** a task or section of a workflow can name the role that does it or signs it off ("3 month check: case worker", "sign off: sign-off supervisor", "evaluation: evaluator"), and the work goes to whoever holds that role in the cluster. The evaluator fits the MEAL checks, the sign-off supervisor the partner's sign-off before MWF review. A role could also be set for one beneficiary later (a case worker per child).
- **Flow:** Assignment finds partners active for the benefit that implement the project. Allocation places the work order on a beneficiary within the project, in a cluster with space. A gift with no project is general. A gift for a benefit the project does not offer becomes an exception and goes to Unallocated for a person to decide.
- **Build order:** the Projects register (name, CRM names, benefits offered, implementing partners, beneficiary count), then clusters inside a project with their roles, then the beneficiary register, then Assignment and Allocation.

- **Roles exist at every level**, so they can follow the hierarchy: a **project role** (school principal) and **cluster roles** (classroom teacher), and later a beneficiary role (case worker per child). The list of roles is configurable per level.
- **A role can hold several people** (two caretakers). They are **chosen from a given list**: the partner's contacts, with a person added from the same place when missing.
- **A project is created two ways.** Manually in OUTCOMES at any time (this already exists as New project), and from a CRM project name that appears on gifts. Today that second way is a list of "Names the CRM uses" where a person puts each name into a project. It is not yet automatic. ## 153. Custom donations to a project accumulate in a project fund, spent on items (23/11/2026)

Design agreed with Faisal, not built yet.

- A **custom donation** reaches OUTCOMES with its project from the CRM transaction (for example a custom amount through the Dadyal Orphan Complex page). It is a directed gift, and it is assigned to that project. It is **parked in the project's fund** and goes no further. The gift's stage reads Gift, with the note "In the project fund".
- The fund is a **derived figure for reference**: the value of the project's custom gifts minus what has been spent on items. OUTCOMES does not manage money. The accounting stays in Salesforce and QuickBooks.
- **Spending the fund:** a person chooses **items that are already configured** and a **quantity of each** (bricks, land, sponsorship). The fund is converted into quantity of those items. That automatically creates the **work orders** of those items, with **units already worked out from each item's own settings** (its bundle and the Work order decision of its workflow). Nothing is unitised by hand. The work orders are released at once, since the money is in, and then go through Assignment to one of the project's vendors, active for the item and with capacity, and on through Confirmation, Allocation and the rest of the workflow.
- **One fund can be spent on several items over time.** What is not spent stays parked. A person cannot spend more than is available. Each work order keeps which custom gifts funded it, so it can be traced.
- **Cost of the spend:** quantity times the item's catalogue price when the CRM has one, otherwise the person types the cost. It is for reference, and it reduces the available amount.
- Custom donations that name a project that is not matched yet **wait for a person to match it** and are not treated as general (Faisal, 23/11/2026). Only gifts with no project, or Where Needed Most, are general.
- Supersedes the "Custom donations go to" setting that was proposed: there is no default benefit, and the choice is made when the fund is spent.
- To build with the Projects register: a **Fund** section on a project (the available amount, the parked gifts, and a Spend on items action that makes the work orders).

## 154. The Projects register: benefits offered, vendors in priority order, one-click create (23/11/2026)

First step of the build order in 152 and 153.

- The Projects page was already there (decisions 66 and 76). It now shows, for each project, its name, the other CRM names it answers to, the **benefits it offers**, its **vendors in priority order**, and its gift count. A project with no vendor says so, and its gifts wait for a person.
- **Benefits offered** (`itemIds` on the project): tick the gift items the project offers. None ticked offers any. A gift for a benefit the project does not offer is an exception, so it goes to Unallocated for a person to decide. Rule: `projectOffers`.
- **Vendors in priority order:** the order of the partners on the project is the order they take work: the first until it is full, then the next. The form has arrows to change the order. Rule: `projectVendors` gives the vendors a work order of an item can go to, in the project's order, only those that are eligible (active, approved, delivering the item, capacity not 0) and only if the project offers the item. The Assignment process will use it.
- **Create project in one click** beside each CRM name that is in no project. It makes the project at once, named after the CRM name, offering the benefits seen with that name on gifts (`itemsSeenWith`), and with no vendor yet. The earlier "New project from this name" opens the form instead. The CRM name matches its project from then on.
- Not built yet: a setting to create projects automatically as names arrive, project roles, the project fund (153), clusters and their roles, the beneficiary count, and using the vendor order in Assignment. A project's name matching a gift's CRM name that is not in any project still does not hold the gift: the rule that a named but unmatched project waits for a person is to be wired in with Assignment.

## 155. A gift that carries a project creates that project (23/11/2026)

- Supersedes the one-click create of 154 as the main route: it stays for anything the automatic rule has not caught. **A gift that carries a project name from the CRM creates that project automatically**, the way an item appears with its first gift. The rule is `autoCreateProjects`. It runs at each CRM pick-up, whenever work orders are read (so gifts that arrived before the rule get theirs), and in the demo. A name is turned into a project only if it is not general and no project already answers to it, by name or by another CRM name, ignoring capitals. Excluded payments do not count, and nothing that exists is changed.
- The new project is named as the CRM names it, with **no vendor yet** (its gifts wait for a person) and **offering any benefit** until a person limits it. It is marked **automatic** in the register, and the mark goes when a person saves it. Only a gift with **no project, or Where Needed Most**, is general.
- This also settles the rule that a named but unmatched project must not become general: there are no unmatched named projects any more, and a project with no vendor makes its gifts wait.

**Where Where Needed Most gifts come from (a question from Faisal).** Nowhere separate. A gift line enters OUTCOMES only when its **item** is marked as needing feedback in the CRM (`item_feedback = 2`). The project on the line is separate. So a general gift is a gift for a feedback-flagged item with a blank project or Where Needed Most. A gift for an item that needs only an acknowledgement (a general donation, Zakat and so on) never arrives. That matches what OUTCOMES is for. **One risk to check with the CRM team:** a custom donation made through a project page (decision 153) arrives only if its item (the Custom Amount item, or whichever item the page uses) is flagged as needing feedback. If it is not, those gifts never reach the project fund.
