# Decisions

Newest at the bottom. Each entry: what, why.

## 2026-11-18

1. **Fresh start.** The prototype (`mwf-impact-tracker`) was built on assumptions now dropped (QuickBooks input, product catalogue). OUTCOMES starts clean, module by module. Prototype code is reused only when reviewed and approved.

2. **Salesforce is the only data source.** QuickBooks is not an input. QuickBooks product tiers (main pot, sub pot, event pot, clearing pot, one product per child) were a workaround for features QuickBooks lacks. Salesforce is more structured.

3. **Transactions are instruction tokens.** We keep what is needed to deliver and report, not to account for money.

4. **No product catalogue.** Instead a small **Project Rules** table: Salesforce **Outcome Activity** to framework (e.g. "Orphan Sponsorship Where Most Needed" to Orphan Sponsorship, 12 months, quarterly report). Expected size: under 100 rows.

5. **Routing key is Outcome Activity, not Designation.** Designation is the fund (e.g. EVENTS, GENERAL AID). Orphan sponsorships taken at events sit under the EVENTS designation; only the outcome activity says "Orphan Sponsorship".

6. **Beneficiaries live in OUTCOMES.** The 2,015 QuickBooks "child products" (IDs like N-A-0365, N-H-0885) become beneficiary records here. Allocation of sponsors to children happens in OUTCOMES.

7. **No duplicate donor profiles.** Store the Salesforce donor ID and a display name. Everything else stays in Salesforce. Later: read and write back through the Salesforce API (connected app).

8. **Centres.** Centres are locations / clusters / agent regions. They send bulk batches.
   - Every gift through a centre keeps the centre as **soft credit** (`Affiliation__c`).
   - If the gift has no individual donor, it is booked to the centre (`Type__c = Community Centre`). Then **the feedback report goes to the centre**.
   - Each line stores: `creditTo` (centre) and `reportTo` (donor, else centre). Centre-only lines are flagged "no individual donor" so staff can add one later.

9. **Every field is configurable.** Per source: map column to standard field, or drop it. Add custom fields: MANUAL (staff fill) or CALCULATED (rule). Each field has type, required flag, transform, default, privacy level.

10. **Drag and drop UI** where users match or sort: field mapping, project rules, import exceptions, allocation, approvals, report templates. Auto-suggest first; users drag only the exceptions. Bulk actions and settings stay as plain forms.

11. **Structured for handover.** See coding standards in `CLAUDE.md`.

## 2026-11-18 (answers from Faisal)

12. **Hosting and Salesforce link.** Developers will build OUTCOMES in the front-end CRM. Its endpoints will feed into Salesforce. So the code needs **API nodes** (a small, separate layer that talks to Salesforce) while business rules stay pure. Salesforce data will sync with OUTCOMES later; for now we work from file uploads.

13. **OUTCOMES sends the donor feedback reports**, not Salesforce. A log can be written back to Salesforce later through the API nodes.

14. **Animal Sacrifice is a Transactional project** (with Water, Rebuild/House, Masjid, Collective marriages).

15. **The OSP Sponsorship System (earlier artifact) is discarded.** Its rules and data are not carried over. OUTCOMES starts fresh.

16. **Transaction classification fields (8).** Every transaction record has these fields, always present: **Channel, Platform, Merchant, Type, Method, Mode, Frequency, Settlement.**
   - Fill each from the source file where a column fits. If nothing fits, **leave it blank**. Never block an import because one is empty.
   - Each field points to a **master list** (configurable). Master lists share common fields: code, name, description, category, status, legal entity, country, effective dates, default, display order, parent, integration reference, audit history.
   - Raw file values are mapped to master values once (drag and drop), then reused.
   - Dependency rules (e.g. Cash cannot have Merchant Stripe) are **warnings only**. OUTCOMES does not reconcile money.
   - Principle: configuration says what is possible; the transaction records what happened.
   - Frequency matters most to OUTCOMES (drives sponsorship lifecycle).
   - Source model: "Transaction Configuration Management" note (Channel, Platform, Merchant, Type, Method, Mode, Frequency, Settlement; Platform is the hub for devices, merchants and settlement).

17. **Order reference must be unique per gift.** A repeated reference is a mistake in the source file, not a normal case, so the import flags it as `duplicate_reference` (never blocks). Found on the real UK file (18 Nov 2026): 50 references of the form EVO-999-999 used twice, rows 248 to 360, all Sadqah General Aid. The source sheet owner corrects them. Also found: 82 individual donors with no Salesforce donor ID (flagged as `missing_donor`).

18. **Instalments come from the source, not from OUTCOMES.** The number of instalments is normally set in the product configuration of the platform that took the donation, and OUTCOMES must not duplicate product configuration. So the Salesforce export needs to carry the count (to be requested). Until it does, a commitment with no count shows **Indefinitely**; one-off gifts stay blank; a real count in a source overrides it. Consequence for Module 2: Project Rules should not hold duration or instalment counts (this narrows the example in decision 4). Revisit when Module 2 starts.

19. **Only the Upload file is loaded each time. The code book is configuration.** The SF META tab changes rarely, so it is loaded once and saved with the setup (in this browser for now). The page calls the daily file the "Upload file". Auto-matching is as wide as is safe (exact Salesforce names, then names and aliases from other MWF sheets, marked "by name"), and a downloadable template shows the exact format that matches everything. Where the setup and code book are stored long term is for the developers (the setup text format stays the same).

20. **Automatic feed by batch.** Admin agents add gifts to the Google Sheet in batches. Each gift carries a batch number (`GiftBatch.Name`, for example GB-000000071). A scheduled job (cron) picks up finished batches that have not been imported yet, runs the saved setup and code book, and sends problems to an exceptions list instead of stopping. Nobody uploads files by hand. Rules: a gift with no batch number is held back; a batch is imported once; a batch edited after import is flagged "changed", not imported again silently. The scheduled job and the Google Sheets connection (read-only) are API nodes for the developers (decision 12). OUTCOMES holds the pure batch planner. Manual Upload file stays for testing and one-off files.

21. **Batch audit.** Items can be added to, changed in or removed from a batch after it is finished and imported. A quick audit compares each imported batch with the sheet as it is now, gift by gift (each gift has its own fingerprint, so one changed gift is found without re-reading the whole batch). It reports: **added** (a new reference under an imported batch number), **changed** (same reference, different content), **removed** (imported but no longer in the sheet) and **moved** (now under another batch). Nothing is lost silently. The audit is a pure function in OUTCOMES; running it on a schedule is part of the developers' job (decision 20).

22. **Google Sheets by Google sign-in, read-only.** The page reads a Google Sheet after each person signs in with their own Google account, using only the `spreadsheets.readonly` permission. Who can read a sheet is controlled by the sheet's sharing (Viewer), not by OUTCOMES. The access token is kept in memory only (never stored or logged) and expires in about an hour. The Google client ID is public and is entered once (`docs/GOOGLE-SETUP.md`). Google's script is loaded from accounts.google.com. A scheduled job cannot use an interactive sign-in, so the developers' pick-up job (decision 20) should use a read-only service account with the same `sheets-api.ts` logic. The sheet data is processed in the browser, and contact columns are still dropped before anything is saved. (Partly superseded by decision 24: people log in through the CRM, and the sheet is read by a service account. The manual Google sign-in stays only as a testing tool.)

23. **White-label and multi-organisation.** OUTCOMES is built so other organisations can use it, not only MWF. Every record, setup, code book, master list, role and setting belongs to an **organisation**, and one organisation never sees another's data (enforced on the server by the API nodes, tested). Words that differ between organisations (donor, centre, beneficiary, designation) and branding (name, logo, colours) are **configuration per organisation**, not fixed text. MWF terms stay as the MWF starter defaults. The pure logic already takes its setup as input, so it stays organisation-neutral.

24. **Login comes from the CRM.** The CRM already has a login, so OUTCOMES does not add its own. The CRM passes the signed-in person (id, organisation, roles) to OUTCOMES, and the server checks it on every request. OUTCOMES decides what each role may do. The sheet is read by a read-only service account per organisation (decisions 20 and 22), not with each person's Google credentials, so people only see what their role allows.

25. **Roles are configuration, not code.** An organisation admin creates and edits roles in Settings. A role has a code, name, description, status and a list of **permissions**. Permissions come from a fixed catalogue that each module registers (for example import.run, mapping.edit, beneficiary.view, donor.contact.view, report.send, settings.manage). A role also has a **data scope**: all, own group (centre, institute, house or cohort), assigned records only, or own record only. A new organisation starts from a starter pack of roles it can change. Roles that are about people in the data (beneficiary, student, carer, warden) are kept separate from login roles, see the open question.

26. **Generic model, with sources as adapters.** OUTCOMES also works standalone, for organisations with no CRM that upload files by hand or connect another way, and whose columns differ. So the solution is built in three layers: (1) a **generic model** whose field names say what a thing means, not what a source calls it; (2) **source adapters** (file upload, Google Sheet, API or webhook, and CRM connectors such as Salesforce) that bring rows in; (3) **organisation configuration** (labels, column mapping, value mapping, lookup lists, roles). Everything specific to Salesforce or MWF (column names like `Legacy_Reference_No__c`, the designation JSON, the SF META layout) moves into a **Salesforce preset** that pre-fills the mapping. It is one preset among others, and an organisation with no preset maps its own columns. Consequences: (a) a transaction can arrive as one row per transaction with a lines column, or as one row per line, grouped by reference; (b) lookup lists (IDs to names) are optional, because a source may carry names directly; (c) which fields are required is set per organisation, so a supporter ID is required only where a CRM provides one; (d) the login is pluggable: the CRM's login where there is a CRM (decision 24), otherwise a built-in or Google or Microsoft login. The coding standard "use Salesforce terms" now applies to the Salesforce preset only.

27. **Module 1 rebuilt on the generic model (18 Nov 2026).** Generic vocabulary confirmed: Transaction, Line, Supporter, Fund, Outcome, Group, Commitment. The Salesforce specifics (column names, the designation JSON, the SF META layout, MWF wording) are one preset. Lookup lists are optional configuration inside the setup. Three lines layouts. Required fields per organisation. A "feedback items only" switch skips total checks for partial uploads. New checks: future date, rows of one transaction disagree. Setup format is now version 2 (older saved setups are ignored).

28. **For MWF, configuration lives in the CRM and OUTCOMES reads it (accepted 19 Nov 2026, from reading mwf_crm).** The CRM (PHP and MySQL) already holds the catalogue (items, variants, bundles, projects, causes, campaigns, intentions), transactions (`crm_transaction`) with line items (`crm_transaction_detail`, each with item, project, cause, post and intention), payment mode, merchant, channel, agent, subscriptions, roles with data scope, and a Salesforce push. So OUTCOMES does not keep its own product or project configuration. A **CRM feed** supplies paid transactions and lines plus the reference lists (items, projects, causes), and OUTCOMES creates **work orders** from lines that need feedback. In OUTCOMES this is a preset ("MWF CRM") next to the Salesforce preset, so other organisations are unaffected (decision 26). The CRM item already has `item_recurring` and `frequency` (for example 12), so the instalment count of decision 18 can come from the catalogue. The CRM has no "needs feedback" or framework flag yet, so one must be added in the CRM, in one place. Answers from Faisal: the feedback trigger is at **item level**, and the feed is a **database view**. Nothing in the CRM repo has been changed.

29. **OUTCOMES is standalone and takes its configuration from the organisation's CRM (19 Nov 2026).** The things needed to manage work orders (instruction tokens) are universal: any charity that sends feedback reports has them configured in its CRM one way or another (items, which need feedback, instalments, payment details, supporters). OUTCOMES does not duplicate them. A CRM connector (a preset plus a read-only database view or equivalent) maps the CRM's fields and extracts its configuration, so the configuration stays in sync with the CRM and has one source. OUTCOMES then focuses on the **work order, the token and the project journey** (routing to a framework, delivery, tracking, feedback reports). Where the CRM already does something, OUTCOMES uses it rather than rebuilding it: **email and communication** go through the CRM, and the **supporter profile** is viewed in the CRM interface. OUTCOMES keeps only the supporter ID and display name (privacy rule). An organisation with no CRM still uses upload or Google Sheet sources and its own setup (decision 26).

30. **Independent build, two ways in, and reporting back (19 Nov 2026).** OUTCOMES is built independently of the CRM repo and branches (nothing is built on the CRM branch). MWF adds the item-level "needs feedback" trigger in the CRM itself, in its next push. The connector can read the CRM **through a database view or through an API**, so it is a pluggable reader behind one interface, and the choice is per organisation. The link is two-way: the CRM is the **data input** (transactions, lines, items, instalments), and OUTCOMES **reports back to the CRM** (delivery status and feedback reports) so the CRM's donor portal and communications can show and send them. The return path is a write interface in the connector, kept separate from the read side, and it writes only status and report links, never money or contact details.

31. **Frameworks live in OUTCOMES, not in the CRM (19 Nov 2026).** Project management (frameworks such as Orphan, Hifz, Water, with their stages, rules and reports) is a gap in charity CRMs, so it is the part OUTCOMES owns. The CRM supplies only the item and the yes/no trigger "this item needs feedback" (decision 30). **Which framework an item belongs to is set in OUTCOMES**, by mapping CRM items to frameworks (auto-suggest first, then drag and drop to correct, as in Module 1). An item flagged in the CRM but not yet mapped to a framework shows as **unrouted** for staff to resolve, and never blocks. A framework is optional per organisation: an organisation with none can still receive tokens and track them with a default simple journey. Later, once matured, OUTCOMES may be embedded in the MWF CRM as a connected module, but the product stays a white-label that talks to many CRMs through connectors (decisions 26, 29, 30). So the MWF CRM item carries only the trigger, not the framework, and Module 2 (Project Rules) owns frameworks.

32. **Access comes from the CRM by a one-click launch, with no user management in OUTCOMES (19 Nov 2026).** Where there is a CRM, people sign in to the CRM and click an "OUTCOMES" button that opens OUTCOMES in a new window, already signed in. How it works: (1) the CRM shows the button only to people whose CRM role has an OUTCOMES permission (the CRM already has a Roles and Permissions matrix, so no new user panel is built); (2) clicking makes the CRM create a **short-lived, single-use, signed launch token** (lives about a minute) holding the person's id, display name, organisation, and the OUTCOMES permissions their CRM role gives them; (3) OUTCOMES checks the signature on its **server**, starts its own session and removes the token from the address; (4) the session is short and is refreshed by asking the CRM again, so removing someone in the CRM removes their access at the next refresh. OUTCOMES stores no passwords. The permission names OUTCOMES needs (for example `outcomes.access`, `outcomes.view_work_orders`, `outcomes.map_frameworks`, `outcomes.settings`) are registered in the CRM's permission matrix, and OUTCOMES' own roles and data scope (decision 25) become a mapping from CRM roles, not a second list to maintain. An organisation with no CRM still needs a login, a small pluggable one (decision 26), but that is outside the CRM-connected product. This needs a small **server part** in OUTCOMES (token check, session), which the browser-only page cannot do, so it is developer work and an open build decision (decisions 24 and 25 are refined by this).

33. **Connected mode is the main screen, import is for other sources (19 Nov 2026).** With a CRM connected, OUTCOMES shows **work orders** that arrive from the CRM feed, already limited to items flagged as needing feedback (decision 30), so there is nothing to import. The Module 1 import and mapping page stays as the way in for organisations with no CRM, and as a testing tool. The home screen should show work orders (ready, unrouted, needs review), not the import page.

34. **OUTCOMES has an application shell that matches the CRM, grown as the product grows (19 Nov 2026).** Because OUTCOMES will have many pages, menu items, frameworks and dashboards, it starts from a proper ERP or CRM style shell (side menu, top bar, page area, cards and tables) that follows the MWF CRM's look (blue gradient menu and header, Inter font, tinted page, white cards), instead of one tool page. The menu is driven by the CRM role's permissions (decision 32), so a person only sees what their role allows. The shell is in `app/` (open `/app/` with `npm run dev`). Colours are variables, so another organisation can re-brand it (decision 23). Module 1's mapping page stays reachable under "Other sources" until it is moved inside the shell. The look is plain CSS for now. Whether the developers move to a component library or the CRM's own theme is for them to decide when the stack is confirmed (open question on the stack).

35. **Item to framework mapping works by suggest, drag and drop, and never moves work in progress (19 Nov 2026).** Staff sort the CRM items that need feedback into frameworks by dragging them (or tapping an item and then a framework). Suggestions come from whole-word matches of a framework's keywords in the item name, are shown as hints and applied only when accepted, and a tie suggests nothing. Sorting an item routes its unrouted work orders, but work orders that already have a framework keep it, so delivery in progress never changes silently. Each framework holds a unit, a feedback cycle, a report type and its keywords, and no duration or instalments (decision 18). Removing a framework returns its items to Unsorted. Built as Module 2 (`modules/02-project-rules/`).

36. **Three levels: items, frameworks, categories (replaced by decision 40) (19 Nov 2026).** Many CRM items cluster into one framework (for example several orphan sponsorship items into Orphan Sponsorship), and frameworks are grouped into **categories** of framework. MWF's starting list, from the earlier discussion (confirmed by Faisal, 19 Nov 2026): **Sponsorship** (Orphan Sponsorship, Hifz, School, College/Uni, Aalim, Homestay), **Transactional** (Water, Rebuild/House, Masjid, Collective marriages, Animal Sacrifice, decision 14), **Livelihood** (Rozgar, Rickshaw), **Microfinance** (Loans), **B2B** (no frameworks listed yet). Categories are configuration per organisation (decision 23), so another organisation has its own. A category sets the feedback cycle a new framework starts with (for example Sponsorship quarterly, Transactional once when delivered), and staff can change it per framework. What else a category changes (for example sponsorship frameworks hold beneficiaries and renewals, transactional ones deliver once and report) is built with Module 5 (Frameworks) and is not decided yet. Removing a category keeps its frameworks.

37. **Hosting the demo on Vercel (19 Nov 2026).** The demo (the shell and the Module 1 page, with invented data only) is published to Vercel from this repo with `vercel deploy --prod` (project `outcomes`, settings in `vercel.json`). It is a static site, so there is no server yet and nothing is stored. The deployment is behind Vercel's sign-in (Deployment Protection), so only people with access to the owner's Vercel account can open it. No real donor, child or CRM data may be put on it. Automatic deploys on every push need the Vercel GitHub app installed on the repository, which is not done yet. The server parts (decision 32 launch token, storage, pick-up job) still need a host and stack decided with the MWF developers, and Vercel is one option (serverless functions).

38. **Server built as Vercel functions with a swappable store (19 Nov 2026).** The server parts are Node and TypeScript in `api/` (thin) and `modules/00-platform/` (logic as plain functions, tested without a network): sign-in from the CRM launch token (decision 32), per-organisation storage, and the pick-up (decisions 20, 28 to 31). Storage is an interface with a memory version (tests, demo) and a Postgres version (Neon through Vercel), so the MWF developers can swap the database or host the same code elsewhere. Sessions last one hour and the person reopens OUTCOMES from the CRM, because refreshing by asking the CRM needs a CRM endpoint that does not exist yet. The scheduled pick-up runs daily (free Vercel plan limit), plus "Run pickup now". When someone sorts an item into a framework, its unrouted work orders are routed immediately, and routed ones are never moved. The CRM read token is never stored in the database, only the name of the setting that holds it. Until a database is connected, a temporary memory store is used and the page says nothing is kept.

39. **A pretend CRM for testing with live input (19 Nov 2026).** Until MWF's CRM has the item-level trigger and a feed, OUTCOMES can be tested against Module 1d, which behaves like a CRM: it produces a feed in exactly the CRM-FEED-SPEC format and new gifts arrive every 5 minutes, worked out from the clock so nothing is stored. Some gifts start pending and turn paid, some fail, and some are later deleted, edited or replaced, so the review list is exercised. An organisation whose CRM setting is `demo` uses it, through the same reader interface as a real CRM, so nothing in the pick-up changes. A test sign-in (`/api/demo-login`) opens the organisation `demo` as an administrator. Reason: Faisal needs to test with realtime input before the CRM work is done. Rules: the test sign-in answers 404 unless the server has `DEMO_LOGIN=1`, it can only open the `demo` organisation, and it is meant for a protected test server only. Remove `DEMO_LOGIN` to switch it off.

40. **Two levels: items and categories. The framework is a property of the category (19 Nov 2026).** Decision 36's three levels (items, frameworks, categories) meant sorting twice for one journey, because the items in a category need a similar journey anyway. Now an item belongs to a **category**, and the category has properties: its name, the words that suggest it, and its **framework**, the settings that decide the flow of every order in the category (unit, feedback cycle, report type, and later the stages). Work orders are routed to a category (`categoryId`). Sorting is one drag. The Frameworks page became the **Categories** page. The permission `outcomes.map_frameworks` keeps its name so the CRM specification does not change. Setup saved in the old shape is shown as empty and starts again from the MWF starter categories. Replaces decision 36.

41. **The CRM's feedback trigger and where instalments come from (19 Nov 2026, from reading mwf_crm again).** The CRM now has the item-level trigger: `crm_items.item_feedback` (migration 074), 1 = Acknowledgement only (the default for every item), 2 = Feedback report. OUTCOMES' MWF settings are trigger column `item_feedback`, yes-value `2`. An older saved setup with the first guess (`needs_feedback`) is moved to these automatically. **Price, frequency and instalments are not set on the item.** They are configured on the catalogue price list line, and copied onto the donation line (`crm_transaction_detail`: `id_vdetail`, `frequency`, `is_continuously`, with the plan's `installment_limit` on `crm_subscriptions`). So the feed carries `is_recurring` and `instalment_count` **per line**, and decision 18's rule stands: no count or a plan until cancelled shows Indefinitely, a one-off stays blank. This replaces the item-level `item_recurring` and `item_frequency` of decision 28. Nothing in the CRM repo was changed. The CRM has no feed view or API for OUTCOMES yet: the column sources are in `docs/CRM-FEED-SPEC.md`, for the CRM developers to confirm.

42. **Stopgap: run OUTCOMES on the CRM's Export Centre files (19 Nov 2026).** The CRM has no feed view or API yet, but it has an Export Centre. Three CSV exports stand in for the feed: Donation lines (paid, one row per line), Catalogue items (the `Feedback type` trigger per item, joined on item code = Item SKU) and Recurring plans (instalment count, joined on the line's Subscription ID = Plan ID). A pure adapter (`modules/01e-crm-export-adapter/`) turns them into feed rows in the shape of `docs/CRM-FEED-SPEC.md`, so everything after it is unchanged. Real files live in `real-data/`, which git ignores, and are never committed or printed (CLAUDE.md privacy). Known limits: the export has no centre, no deleted or replaced markers (replaced orders cannot be detected) and no line total, and a recurring line whose plan is missing from the plans file shows Indefinitely. The proper feed view or API (decision 28 to 31, 41) still replaces this later.

## Open questions

- Categories: the starting list is confirmed (decision 36). What should each category change besides the default feedback cycle? (Sponsorship: beneficiaries, allocation, renewals. Transactional: deliver once, then report. Proposed, for Module 5.)

- Salesforce feedback module is not built yet, so there is no ready report export. For testing we use the "SF Upload" and "SF META" tabs of the UK upload sheet (see `DATA-SOURCES.md`).
- Who marks a batch Ready (a column on the sheet is simplest), and when is it safe to pick up a batch while several agents add to the same sheet?
- Is one batch number one upload event, and what should happen to the gifts that currently have no batch number (125 of 525 in the UK file)?
- Work order: one per paid line with a feedback item, and for recurring giving one per paid instalment linked to its subscription (proposed).
- Roles list: beneficiary, student, carer, warden and house carer may be people in the data rather than people who log in, and a cohort is a group, not a role. Which of vendor, partner, admin, agent, beneficiary, student, cohort, carer, warden and house carer need a login, and what should each see? Proposed: two configurable lists, **login roles** (what a signed-in person can do) and **party types** (who someone is in a framework, such as beneficiary or carer, with groups such as cohort or house), with common fields as in decision 16.
- Launch token: built with a shared secret (decision 38). Would the CRM developers prefer public key signing? Who hosts OUTCOMES long term, Vercel or MWF's own servers?
- Session refresh by asking the CRM: needs a CRM endpoint that says whether a user still holds the OUTCOMES permissions.
- How often should the job run, and how often the full audit (for example every pick-up for new additions, and a full audit daily)?
- What happens to audit findings: late additions imported automatically and listed for review, but changed or removed gifts always held for a person to approve (suggested, because reports or allocations may already depend on them)?
